# 2. Architecture

Snapshot: 2026-11-16, `main` after `666fd35`. Detail lives in each product's `AGENTS.md` and `docs/command_reference.md`.

## 2.1 The board (PFM-Controller V4)

| Part | What it does here |
|---|---|
| **STM32G474QET6** | Arm Cortex-M4F at 170 MHz, 512 KB flash in **two banks** (used for safe firmware updates), 128 KB RAM. |
| **HRTIM1** (in the MCU) | Six timing units (A-F) plus a Master timer, clocked at 170 MHz (one count = 5.88 ns). Generates every drive signal, with complementary outputs, hardware dead time, and hardware fault inputs that force outputs safe without the CPU. |
| **TIM2-TIM5** (in the MCU) | Capture the period of incoming fiber signals on the six `PFM_Input` pins (XREX feedback; bench self-checks on HBRIDGE). |
| **ADC1 / DAC** (in the MCU) | HBRIDGE closed-loop voltage feedback (PA0, PA1, PB0, ...) and two DAC outputs (PA4, PA5) used for hardware-in-the-loop tests. |
| **W25Q128 QSPI flash** (16 MB, external) | Saved profiles and the board identity. XREX profiles use 0-64 KiB (magic `WSPF`), HBRIDGE profiles 64-320 KiB (`HSPF`), identity the last sectors (`0xFFD000`/`0xFFE000`). The two products never touch each other's region, so a board can switch products without losing the other's data. |
| **USART2** | The command link, 115200 8N1. Wired to a WIZnet serial-to-Ethernet module and to a USB-serial header. |
| **Fiber-optic transceivers** | Drive, feedback and fault signals to and from the supplies (noise immunity, isolation). |
| **GPIO** | 12 gate-driver/fault inputs on PE0-PE11 (both products, different meanings), interlock and trigger inputs (PF13, PF15), enable outputs (PG0-PG7 on XREX; PG0 is CHARGE on HBRIDGE), LEDs. |
| **PC10 = HRTIM1 FLT6** | A hardware fault input: a LOW on it disables the outputs in silicon, with no software in the path. |
| **SWD header** | ST-Link programming and debugging. Must be used with the NRST wire disconnected (see `06_known_hardware_issues.md`). |

The full pin map with each product's meaning is `firmware/<product>/docs/pin_mapping_v4.csv`.

## 2.2 Firmware structure (both products)

Bare metal (no operating system), C11, ST's HAL library. The code is layered, and a checker enforces the layers at every build:

```
Core/              generated by STM32CubeMX: main(), interrupt vectors, clock setup. Only one-line calls are added by hand.
src/config/        ctrlr_config.h: every compile-time constant (channel count, limits, defaults, version string)
src/drivers/       hardware-independent interfaces (headers only): hrtim.h, uart.h, nvstore.h, board_io.h, ...
src/bsp/stm32g4/   the ONLY code that touches registers, the HAL or interrupts; implements src/drivers/
src/middleware/    scpi/: the command parser and reply helpers, no hardware and no product knowledge
src/app/           the product: control/ (state machine, shot engine, PID), protection/ (faults), settings/ (profiles),
                   commands/ (one cmd_<subsystem>.c per command group), task_*.c (main-loop tasks)
tests/             host unit tests: the hardware-free logic compiled and run on the PC (make -C tests)
```

Dependencies point one way: `app -> middleware -> drivers <- bsp`. Application code never includes HAL headers. This is what
makes most of the logic testable on a PC with fakes, and it is why a feature that needs hardware gets a new `src/drivers` interface
plus a BSP implementation instead of a direct register access.

**Main loop and interrupts.** `main()` initialises the hardware, then calls `App_Poll()` forever. That runs non-blocking tasks
(`TaskX_Poll()`): command handling, fault polling, telemetry. Time-critical work runs in interrupts:

* the HRTIM Master per-period interrupt (loads the next switching period's values),
* the control tick (XREX PID at the Master rate; HBRIDGE closed loop on each ADC DMA block, default 10 kHz),
* fault input edges (EXTI) and the UART receive interrupt.

Priorities matter and were set deliberately (`AGENTS.md` and `07_fragile_software.md`). Fault handling that must be immediate is
done in hardware (HRTIM fault input) or at the start of the edge interrupt; anything slow is deferred.

**Commands.** `src/middleware/scpi/scpi_parser.c` matches each line against `src/app/commands/command_table.c` (long and short forms,
case-insensitive, `?` for queries). Handlers parse arguments with strict helpers (`Scpi_ParseLong`, ...) and reply with `Scpi_ReplyOk` or
`Scpi_SendErr`. Error codes are a frozen list (`scpi_err.h`, `docs/scpi_conventions.md`).

**State machine.** `src/app/control/state_machine.c` owns `IDLE / ARMED / FIRING / FAULT`. Only `SetState()` may change the state (it
also drives the LEDs). Commands are gated on state (for example: firmware update needs `IDLE`, a shot needs `ARMED`).

## 2.3 XREX specifics

* **Output.** Each of the four channels runs on its own HRTIM timing unit with its own period. It is updated through that unit's
  shadow registers at its own roll-over ("Possibility 3" in `docs/Transrex/hrtim_divergent_period_timing.pdf`), so the four
  frequencies are fully independent.
* **Control.** `src/app/control/pid.c` runs a fixed-rate PID per channel. It reads the latest measured feedback period (TIM2-5 capture),
  converts to Hz, computes, clamps (slew and range) and writes the new period. **The fixed control rate decoupled from the carriers
  is deliberate; do not "simplify" it into a per-channel self-clocked update.**
* **Shots.** `ARM`, then `SHOT:STARt` (or a PF15 trigger edge): ramp, flat top and ramp down to each channel's demand current.
* **Protection.** `src/app/protection/xrex_io.c` evaluates per-channel water, temperature and Enerpro faults (on the PE0-PE11 pins),
  overcurrent (polled pins), and ENA_OUT/CONTACT_OUT feedback. Fault responses use `PFM_ForceStopSoft()` so that the ramp-down can run
  (the Master counter must keep running; see `07_fragile_software.md`).
* **Simulator target.** The same source builds a "Transrex simulator" image (`--target simulator`) that makes a second board imitate
  four Transrex supplies for full-system bench tests.
* **Legacy table mode** (`TABle:*`, `FIRE`) inherited from the predecessor project is kept as a bench fallback only.

## 2.4 HBRIDGE specifics

* **Output.** Timers A, B and C drive U, V and W. All three are reset by the Master timer: U at the Master period, V at Master compare 1
  (1/3 period), W at compare 2 (2/3 period). This phase locking is what gives 120° spacing. Each output's SET is on a dedicated compare
  (CMP3) so that it wins a same-instant collision with RESET (the bug that dropped pulses on fast ramps, fixed 2026-09-09).
* **Shot engine.** `SHOT:*` stores up to 500 setpoints. `src/app/control/shot_profile.c` interpolates one switching period at a time into
  a ring of per-period entries; the per-period interrupt (`pfm.c`) consumes it. A 0 Hz setpoint gates the outputs off phase by phase
  at the end of each phase's own period (`HRTIM1_GapEnter/GapExit` in `hrtim.c`) while the counters keep running, so the restart is
  phase-locked.
* **Closed loop.** `src/app/control/control_runtime.c` has one `closed_loop_t` per phase (`closed_loop.c`, `pid_core.c`, `feedback.c`).
  ADC1 scans the inputs on a timer trigger into circular DMA; each DMA block is one control tick. Feedforward from a plant model
  (HVPS resonance curve, Limiter linear) plus PID. Overvoltage, ADC full scale and dead feedback line are faults. `PID:LOOPMODE`
  chooses open or closed per phase; mixed runs are allowed.
* **Protection.** `gate_driver.c` and `gds_inputs.c`: the 12 GDS pins interrupt on both edges, are evaluated against the polarity in force
  and the enable mask, and any fault calls `PFM_ForceStop()` at once. There is one fault type (`GENERAL`). PC10 also stops the outputs in
  hardware.
* **External trigger.** PF15's rising-edge interrupt (priority 1) only checks and counts. It pends a software interrupt (the unused
  CORDIC vector, priority 2) that starts the shot, because a start takes a few hundred microseconds.
* **CHARGE.** TIM20 CH1N on PG0, independent of the state machine by design.

## 2.5 Saved profiles

`*SAV <slot>` serialises every operator setting as tagged records `[field id][channel][length][value]` plus the HBRIDGE tables
(shot, target, HVPS curve), streamed to flash because RAM is short. Two alternating copies per slot, header written last with a CRC,
so a power cut during a save never destroys the previous good copy. `*RCL` applies each value through the same setter a command
uses, reports `APPLIED`, `FAILED` (with names), `GDSOFF` and `IGNORED`. **Field ids are a frozen contract**: never renumber or reuse
one. HBRIDGE stores, among others, the supply mode, all loop modes and gains, feedback calibration, GDS configuration, dead time and
the phase choice. Run state, CHARGE, the trigger enable, `DEBUG:FAULT:BYPASS`, DAC outputs and simulation settings are never stored
on purpose. Details: `firmware/hbridge/docs/saved_profiles.md`.

## 2.6 Firmware update and boot

`FWUPdate:BEGin/DATA/END/SWAP` writes the new image into the flash bank that is **not** running, checks its CRC, then flips the boot
bank (BFB2 option bit) and resets. The old image stays in the other bank (`fw_update.py --rollback`). Every boot prints a three-line
`!BOOT` banner (version, commit, bank, state, serial, reset cause). The update requires `STATE IDLE`. An update image is refused if
its product name differs (HBRIDGE will not accept an XREX image and vice versa); changing a board's product needs the ST-Link.

## 2.7 Host side

* `host/wham_hub.py`: one instance per board, on the lab server, the only client of that board's bridge. Clients connect to its TCP
  port (5101 XREX-CTRL, 5102 LMTR-CTRL, 5103 ECH-HVPS through an ssh tunnel). It logs JSONL per board per day, checks identity
  (`expect_serial`), announces dangerous commands (`host/dangerous_commands.py`) to other clients. **No authentication.**
* `firmware/<product>/python/`: build (`wham_build.py`), update (`fw_update.py`), network client (`net_client.py`, in `host/` since 2026-11-20; a stub remains here), shot tests
  (`pfm_shot_test.py`, `pfm_gap_test.py`), consoles, report generators.
* `host/operator_ui/`: a local web console for operators (connect through a hub, ARM/FIRE with confirmation, shot builder, recording).
* LabVIEW front ends use the hub in quiet mode (`docs/labview_hub_guide.md`).
