2026-10-05  —  PHASe:ENAble / PHASe:SELect: choose which of the three phases U, V, W drive their outputs
-----------------------------------------------------------------------
  Branch phase-enable. Request: a command so an operator can output with only U and W, only W, or any combination.
  The mechanism already existed (pfm.c's durable per-channel enable array -> HRTIM1_PWM_Start(), which leaves a disabled
  channel's pins unconnected while its timer keeps running in step with the Master); nothing exposed it. Added:
        PHASe:ENAble <phases> <0|1> / PHASe:ENAble? [<phase>]   switch the named phases, others unchanged; OK U=1 V=0 W=1 or OK <0|1>
        PHASe:SELect <phases> / PHASe:SELect?                   exactly these on, the rest off; OK UW / OK NONE
        <phases>: letters in any order/case (UW, wu), channel numbers (13, 1,3), ALL (NONE for SELect). phase_mask.c: the pure parser and
        formatter, host-tested (48 checks); PFM_GetPhaseMask/SetPhaseMask.
  Rules: IDLE only for changes (the mask is read at shot start), queries any time; ARM refuses while no phase is enabled (ERR 13);
  all three on at every boot; NOT saved in profiles (a recall must not change which legs are driven); SOURce LOOP (measures Phase U)
  refuses to start with U disabled. GDS fault inputs are NOT masked per phase: the pin map does not say which input belongs to which phase.
  Verified on the simulator with PFM_Input 1/2/3 = U/V/W: for UVW, UW, W, V, U, VW, "1,3" and ALL, exactly the enabled phases' inputs saw edges
  (300 of 300 periods, the others 0), no combination faulted; ENAble/SELect adding and removing, NONE refusing ARM, IDLE gating (ERR 13 while
  ARMED) and argument errors (ERR 12) as designed; the loopback refused with U disabled and ran with it. Not done: a scope check of the phase
  angles for each combination (the design keeps each phase at its fixed place; only the edge counts were measured).

2026-10-05  —  HVPS output is power: frequency -> volts lookup table (CONFig:CLOSEDloop:CURVe:*), linear default, no negative targets
-----------------------------------------------------------------------
  Everett's description of the HVPS plant: the feedback voltage stands in for POWER, which is never negative, peaks at the resonant
  frequency (about 19 kHz) and falls on both sides; raising the output means moving the drive frequency toward resonance (typically a
  start around 20 kHz); the relationship may be assumed linear for now, but a lookup table will be needed because the real one is
  nonlinear and cannot be measured yet.
  Found: the controller's feedforward was ALREADY linear (V = 0 at the band's far edge, Vpeak at resonance); the Lorentzian curve was
  only in the simulated plant, so the earlier HVPS loopback (129/85 mV rms above/below) was a linear controller against a nonlinear
  plant. Changes:
        hvps_curve.h/.c   a table of (Hz, volts) points (up to 32, frequency strictly increasing, volts >= 0, one peak), linear
                          interpolation, inversion on either branch (HvpsCurve_FreqFor), and the linear default builder.
                          Host test test_hvps_curve (125 checks); closed-loop tests added for a loaded table and for refusal.
        CONFig:CLOSEDloop:CURVe:BEGin/STEP/END/CLEar and CURVe? / CURVe:POINt? <i>   (mirrors TARGet:*): a loaded table replaces
                          the linear default for the feedforward and its peak defines where the band starts (RESonance is then
                          ignored); an invalid table is refused at start.
        negative HVPS targets   refused at TARGet:STEP (ERR 4) and again at start (Cl_Start); the Limiter's bipolar target is unchanged.
        SIM:PLANT:SHAPE LINEAR|LORENTZ   default LINEAR (zero at the HVPS band's edges, set from the mode's limits at each start);
                          LORENTZ is the old nonlinear shape, to test a loaded table against.
        simulated plant starts at the first target voltage instead of 0 V (no 20 ms start-up transient in HVPS runs; the DAC loopback
                          sets that level before the first tick).
  HVPS loopback, ABOVE resonance, target 1.0 -> 1.4 -> 0.6 -> 1.4 -> 1.0 V over 100 ms, gains 4000 Hz/V / 200000 unchanged, tau 3 ms,
  Phase U -> PFM_Input_01 -> model -> DAC PA5 -> amplifier -> ADC PA1; all ended IDLE, no fault (error after 5 ms):
        linear plant, linear table       51 mV rms / 78 mV max   (output 19.4-26.0 kHz)   [BELOW: 48 / 77 mV, 13.3-18.7 kHz]
        nonlinear plant, linear table   110 mV rms / 254 mV max  (reaches the 19 kHz floor; overshoots and undershoots)
        nonlinear plant, matching table  37 mV rms / 69 mV max   (19.4-23.0 kHz)
  The matching table (a Lorentzian sampled every kHz, uploaded over CURVe:*) cut the error to a third of the linear-table figure with
  the same gains: the lookup table is what a nonlinear plant needs; gains were not touched.

2026-10-05  —  HVPS loopback: SOURce LOOP now works for the HVPS (measured carrier frequency -> resonance model -> DAC -> real ADC)
-----------------------------------------------------------------------
  The loopback source (entry of 2026-10-02) was Limiter-only (duty). For the HVPS the duty meter's frequency output feeds the
  resonance model, V = gain x vpeak / (1 + ((f - resonance) / width)^2), then the plant lag, the DAC and the real ADC input
  (SimPlant_HvpsSteady; the Limiter/HVPS choice follows the supply mode). Same wiring: Phase U -> PFM_Input_01, DAC PA5 -> amplifier
  -> ADC PA1 (re-checked after the overnight gap: 0.552 x DAC, +18 mV).
  Run: HVPS, SCALE 1 / OFFSet 0, controller and plant VPEAK 1.5 V at 19 kHz (the amplifier path only reaches 1.6 V at the ADC), width
  3 kHz, tau 3 ms, gains 4000 Hz/V / 200000 (untuned, as in the simulated runs), target 0.5 -> 1.2 -> 0.5 -> 1.2 -> 0.5 V over 100 ms.
  Both branches ended IDLE with no fault. ABOVE (output 19.7-24.6 kHz): 129 mV rms / 322 mV max after 5 ms; BELOW (13.9-18.1 kHz):
  85 mV rms / 224 mV max. Both include a start-up transient (the model plant starts at 0 V, the target at 0.5 V; it takes about 20 ms to
  catch up). From 25 ms on: ABOVE 98 mV rms / 198 mV max, BELOW 67 mV rms / 141 mV max; the feedback lags the demand by up to about
  100-200 mV mid-ramp and overshoots the demand by up to 157 mV (ABOVE) / 124 mV (BELOW) at the second 1.2 V peak. The loop is stable;
  the gains are simply not tuned for this plant (nonlinear: gain falls toward the peak and rises away from it).
  Not tested: HVPS duty other than the 50 % default; PFMIN captures and this meter cannot run together (as before).

2026-10-02  —  Loopback test with a stronger low-pass (SIM:PLANT:TAU 6 and 10 ms)
-----------------------------------------------------------------------
  Same loopback run as the entry below (Phase U -> PFM_Input_01 -> model -> DAC PA5 -> amplifier -> ADC PA1, Limiter, +-0.5 V
  triangle over 100 ms, gains 214.286 / 8571.429 unchanged), with the plant low-pass lengthened. No faults in any run.
        tau 3 ms    error 30 mV rms / 44 mV max    duty 8.7-95.0 %
        tau 6 ms    error 46 mV rms / 75 mV max    duty 5.0-95.0 % (touches both limits)
        tau 10 ms   error 59 mV rms / 137 mV max   duty at 95 % for about 5 ms before each positive peak and at 5 % for about 6 ms
                    before each negative one; the feedback only reaches about +0.40 / -0.44 V of the +-0.5 V target
  The limit is physical, not tuning: a 12.5 ms ramp of 1 V through a 10 ms lag needs more than a 95 % duty can deliver, so the
  output saturates and the loop is blind to the rest. Anti-windup behaved: after each saturated stretch the error recovers in a few
  ms with no overshoot. A longer lag needs a slower target (or a bigger vscale), not different gains.

  expresses this; tested on the simulator with scale 2 Vmax / 2.9 and offset 1.45: a +-720 V triangle in a +-900 V range tracked
  to 20 V rms, 34 V max, shot ended IDLE. Added (decided with Everett: keep every voltage in the loop's own units):

                                                 RANGE? = process volts at the top of the ADC range
        FEEDBACK_VMAX_DEFAULT_V (ctrlr_config.h) compile-time default for it; 0 (uncalibrated) for now -- the real divider
                                                 does not exist yet
        low-end clip fault   an ADC reading at code <= 5 for CLIPTime (10 ms) faults (FAULT:SOURces? FB), but ONLY when the
                             offset is non-zero. On a mid-scale-zero range code 0 means -Vmax or a dead/shorted/wrong-channel
                             feedback line, which the loop would read as a huge negative voltage and answer by driving the output
                             up with nothing behind it. HVPS (offset 0, feedback 0 V at the start of every shot) is not affected.

2026-09-30  —  PFM_Input capture rewritten: bounded DMA into the result array (fixes capture loss at high rate)
-----------------------------------------------------------------------
  Symptom: from 100 kHz up, inputs 3 and 4 (TIM5) lost most of a both-edge shot
        (frequency sweep entry above: UN 14 of ~100 edges at 125 kHz, some with
        stale or out-of-order data), TIM2 inputs held up.
  Diagnosis (measured on the simulator, not guessed): rising-only and both-edge runs
        showed NO DMA overrun (worst backlog 8-11 of 32 entries) and the master
        interrupt at 40-65 % CPU, but channel 4's half-transfer callback never ran

        rotation. An event trail (timestamped callback entry/exit) showed each
        16-edge chunk costing about 24 us wall time (HAL DMA handler + chunk loop,
        preempted by the per-period interrupt). Four channels x one chunk per 80 us
        asks for more CPU than exists, so the last channel in line is starved.

        Start_DMA calls took ~20 us with the master interrupt running, so the fourth
        channel started ~80 us (8 periods at 100 kHz) late.

        M+1 edges, or 2M+1 both-edge, at most PFM_INPUT_MAX_EDGES), so each DMA

        are computed from the stamps when PFMIN:DATA? asks. Two DMA interrupts per
        capture per channel, nothing per edge. PFM_Restart() now starts the capture
        immediately BEFORE HRTIM1_PWM_Start(), so nothing is missed and the capture
        includes the shot's start-up period.

2026-09-09  —  Real PFM output falls ~77 periods behind on a long table
               hold: root-caused to a stale NVIC priority inversion,
               FIXED and CONFIRMED on real hardware
-----------------------------------------------------------------------
  Change:  Found while stress-testing the DMA-based PFM_Input capture
        below with progressively less trivial waveforms (an extreme
        zigzag, then a slower ramp/hold(100 periods)/ramp profile). The
        ramp/hold/ramp shot's real HRTIM output was confirmed, via a
        DSLogic ground-truth capture (all 6 channels agreeing, U vs UN
        median error 0.0), to genuinely stall on the wire: it holds one
        frequency for ~187 real periods instead of the table's
        programmed 100, then cleanly resumes the correct sequence ~77
        periods late. PFM:DIAG?'s existing single max-gap diagnostic
        (added the same day for a different, now-closed dead end) could
        not distinguish "one big stall" from "many small repeated
        delays," so a new diagnostic was added: PFM_GetDiagGapLog()
        (pfm.c/pfm.h) logs the raw DWT-cycle gap between every single
        PFM_CycleBoundaryHandler() call for the current shot (up to
        PFM_INPUT_MAX_PERIODS of them), exposed over serial as
        PFM:GAPLOG? (commands.c/commands.h/cmd_parser.c) -- TEMPORARY,
        same debug-command convention as PFMIN:DMASTAT?, meant to be
        removed once this investigation closed.

        The raw gap log immediately showed the real mechanism: not one
        stall, but a spike of ~15000-18500 cycles (~88-109 us) recurring
        roughly every 8-10 table entries, each followed by an
        anomalously short next gap (the classic signature of a single
        delayed ISR entry, not an accumulating one). The recurrence
        interval (~8 periods) matches PFM_Input's DMA capture design
        exactly: a 32-entry circular buffer with a half/full-transfer
        interrupt every 16 captured edges, i.e. every 8 periods at 2
        edges/period.

        Root cause: PFM_Input's DMA1_ChannelN_IRQn (the interrupt whose
        callback batch-processes those 16 edges, pfm_input.c) was left
        at NVIC priority 1 -- a decision inherited from the OLD, now-
        superseded per-edge interrupt-driven capture design, where
        TIMx capture interrupts genuinely needed to preempt
        HRTIM1_Master_IRQn (demoted to priority 2 on 2026-09-08) to
        avoid a real overcapture race. That reasoning stopped applying
        the moment capture became DMA-driven (2026-09-09, entry below):
        the DMA controller grabs each CCRx value in hardware with zero
        CPU/IRQ involvement, so nothing about capture fidelity depends
        on IRQ priority anymore -- only the periodic 16-edge batch-
        processing ISR still runs on the CPU, and leaving IT above
        HRTIM1_Master let its own real (non-trivial) processing time
        repeatedly steal cycles from the table-advance ISR, which is
        what a long run of identical hold entries made visible as a
        large, compounding real-time lag.

        Fix: HRTIM1_Master_IRQn restored to priority 1 (hrtim.c,
        HRTIM1_EnableMasterInterrupt()); PFM_Input's DMA1_ChannelN_IRQn
        demoted to priority 3 (pfm_input.c, PfmInput_Init()), below
        both HRTIM1_Master and the GateDriverStatus EXTI/TIMx_IRQn tier
        (priority 2). Safe because the ~8-period window before the
        circular buffer would actually wrap and lose data is orders of
        magnitude larger than HRTIM1_Master's own ISR execution time.

        CONFIRMED on real hardware, same ramp/hold/ramp shot, before/
        after:
          PFM:DIAG? max gap    18547 cycles (109 us)  ->  5152 cycles
                                                            (30 us -- this
                                                            IS the table's
                                                            own longest
                                                            programmed
                                                            period, not a
                                                            stall)
          PFM:GAPLOG? (full)   repeating ~15-18k-cycle spikes every
                                8-10 entries  ->  every single one of
                                200 entries within normal jitter of its
                                own programmed period, zero anomalies
          PFMIN:DATA? (all 3   198-199/200 captured, OVERCAP=0 -- capture
          active channels)     fidelity unaffected by the IRQ demotion

        PFM_GetDiagCounters()) to test the interrupt-starvation theory
        for the table-advance stall found in the entries just below --
        NOT a plain call counter (a completed shot's call count is
        always exactly the table's entry count regardless of whether
        stalling happened along the way, since PFM_CycleBoundaryHandler()
        only stops once g_pfmIndex reaches it -- that number alone
        can't distinguish "ran on schedule" from "was starved, then
        caught up"). Instead tracks the largest REAL TIME gap between
        two consecutive calls, using the Cortex-M4 DWT free-running
        cycle counter (170 MHz, confirmed same clock as
        HRTIM_TIMER_CLK_HZ) -- reset at every PFM_Restart(), read back
        as "OK <callCount> <maxGapCycles> <maxGapUs>".

        Result, same 100->60kHz decreasing sweep, only PFM_Input_01+02
        active (2 real channels, both genuinely wired): PFM:DIAG? ->
        "OK 200 124818 734" -- 200 calls (as expected either way), but
        a MAXIMUM GAP of 734 us between two consecutive calls. Normal
        gap at ~91-95 kHz should be ~11 us (one real period) -- 734 us
        is ~67x that. This is direct, quantitative proof that
        HRTIM1_Master_IRQHandler() (which runs PFM_CycleBoundaryHandler(),
        priority 2 -- deliberately BELOW every TIM2-5 capture channel's
        priority 1, so real edges are never missed) was starved for
        roughly 67 real periods straight, with just 2 real capture
        channels active -- not a logic bug in the table-advance code,
        and not something that requires many/floating channels to
        trigger.

        DECISION: since capture-channel interrupt load is confirmed as
        the actual mechanism, the planned fix is a DMA-based capture
        redesign -- configure each TIMx to auto-transfer its captured
        CCRx value into a RAM ring buffer via DMA on every edge, with
        ZERO CPU/ISR involvement per edge (versus one full ISR entry/
        exit + HAL dispatch + capture logic per edge today). The CPU
        would only wake up occasionally (a DMA half/full-buffer
        interrupt) to process a BATCH of already-timestamped edges,
        removing capture-channel interrupt PRIORITY/LOAD from
        competing with HRTIM1_Master almost entirely. Not yet
        implemented -- this entry documents the confirmed root cause
        and the planned direction, not a landed fix.

2026-09-09  —  HRTIM SET/RESET collision fix for phase-shifted channels
               (V/W) -- root cause found, real fix applied, pending

-----------------------------------------------------------------------
  Change:  Root-caused the frequency-ramp glitch from the entries just
        below: a real-hardware sweep with PFM_Input_01 restricted to
        phase U (clean, 0 anomalies) alongside a full 6-channel DSLogic
        capture (U/UN/V/VN/W/WN) found V and W BOTH glitching --
        starting as low as ~68-69 kHz, well inside the range U alone
        had suggested was safe -- while U/UN stayed perfectly clean.
        Every glitch's measured duration matched (old period + new
        period) almost exactly (ratio 0.988-1.005 across all 16
        glitches checked), on BOTH V and W -- i.e. one complete real
        SET/rising-edge event is being silently dropped, not a garbled
        or partial one.

        Found the exact documented mechanism via ST's own community
        engineering forum (search "HRTIM PWM transients greater than a
        period"): when a timer's output SET and RESET events fall
        within ~3 HRTIM clock cycles of each other, RESET always wins
        and SET is silently dropped, leaving the output low for one
        extra full cycle. U's output SET is tied to TIMPER = MASTER_PER
        (its ResetTrigger), always far from its own mid-cycle CMP1
        (duty, its ResetSource) -- no collision possible. V/W's SET is
        ALSO tied to TIMPER, but for them TIMPER = MASTER_CMP1/CMP2
        (their own ResetTrigger) -- a point that itself shifts every
        table entry as per changes (phase = k*(per+1)/N), and during a
        fast ramp can land within a few clocks of the PREVIOUS cycle's
        own CMP1 (duty) event, exactly the documented collision.

        FIX (the same one documented in that thread): V/W's output SET
        moved off the un-prioritized TIMPER event onto a dedicated
        CMP3 compare (HRTIM's collision rule favors the higher-numbered
        compare register, so SET now wins ties against RESET's CMP1
        instead of losing). CMP3xR set once at init to a small fixed
        16-tick offset (not duty-dependent, no per-cycle updates
        needed) -- negligible against real period lengths (1200+
        ticks). Deliberately narrow: only channels 1..HRTIM_NUM_
        CHANNELS-1 change; channel 0 and the unused channels beyond
        HRTIM_NUM_CHANNELS (free-running, no MASTER_CMPk race possible)
        keep SetSource = TIMPER.

        Rebuilt clean (zero warnings, text 47140 -> 47252 bytes).
        NOT YET RE-VERIFIED ON REAL HARDWARE as of this entry -- next

2026-09-04  —  Per-phase cold-start settling (real fix, not just jitter reduction)
-----------------------------------------------------------------------------------
  Change:  A fresh DSLogic capture of profile 3 (90% -> 10% ramp) exposed
        that the previous two entries below, while a real improvement,
        hadn't actually gotten the phase-lock settling right -- they
        eliminated the catastrophic U/V/W collision, but connected all
        three outputs together after waiting for a single event (one
        full Master period). Since V/W's own ResetTrigger (MASTER_CMP1/
        CMP2) fires much earlier (1/3, 2/3 of a period), by the time all
        three connected together V/W were already mid-way through
        whatever their comparators had been doing since that earlier,
        still-hidden reset -- exposing a stale/in-progress duty cycle,
        not a clean pulse, and what looked like a "recovery" edge near
        120/240 deg was actually just each timer's own natural TIMPER
        rollover after its hidden reset -- which only lands near there
        by coincidence of that particular duty value, not by design.
        Confirmed by decoding the .dsl capture's raw per-channel data
        directly (per-channel bit-packed L-N/0 files inside the archive).

        Real fix: HRTIM1_PWM_Start() now waits for and connects each
        phase SEPARATELY, at its own reset-trigger event -- new static
        helper HRTIM1_WaitForPhaseAndConnect(), called three times (V at
        MASTER_CMP1, W at MASTER_CMP2, U at MASTER_PER/MREP, in that

        SETx1R/RSTx2R writes, same reasoning as the direct OENR write)
        at the exact moment their flag is observed -- necessary because
        an externally-triggered counter reset does NOT itself generate
        a fresh SET event (confirmed against the capture data), so
        without this the output would still reflect whatever the
        original pre-counter-start force-ACTIVE call left it in, not a
        clean restart. Timer A needs no such re-force: MASTER_PER
        coincides with its own natural rollover, a genuine TIMPER
        SET-source event that already transitions the output correctly
        on its own. Net effect: nothing visible on V/W until 120/240 deg
        after U's first edge, then a clean, correctly-timed,
        correctly-dutied pulse -- not a snapshot of an in-progress cycle.

        Considered and rejected: reverting to relying solely on
        pre-loading step 0's per/compare values (raised directly, in
        chat) instead of delaying output connection at all. Doesn't
        work -- PFM_Restart() already pre-loads those values via
        PFM_ApplyCurrentStep()/HRTIM1_SoftwareUpdate() BEFORE
        HRTIM1_PWM_Start() runs, unchanged since before any of these
        fixes existed, and the original bug happened anyway with that
        pre-loading already in place. The defect was never stale
        register content; it's genuine counter-timing settling that
        only resolves once real time has elapsed, which register values
        can't substitute for.

2026-09-04  —  Masked interrupts during the settling wait's critical section
---------------------------------------------------------------------------
  Change:  Second follow-up to the cold-start phase-lock fix. A fresh
        DSLogic capture after the loop-tightening entry directly below
        showed real improvement (first pulse 200 ns -> 600 ns; U/V/W
        edge-timing error ~700 ns -> ~230-270 ns off target) but a
        genuine, non-shrinking residual remained -- and it varied run
        to run (200 ns, then 600 ns), which pointed away from a fixed
        software-latency floor and toward interrupt preemption:
        HRTIM1_PWM_Start()'s poll runs with global interrupts enabled,
        and SysTick (priority 0, the HIGHEST in this firmware -- see
        FixSysTickPriority()) or USART2 (priority 2, this very FIRE
        command's own reply path) can legitimately preempt the tight
        poll loop for a handful of cycles at exactly the wrong moment.

        Fix: wrapped the poll and the OENR write in __disable_irq()/
        __enable_irq() -- a short, bounded critical section (worst case
        ~385 us for a uint16_t `per`'s longest representable period,
        typically ~10 us at 100 kHz). Since HAL_GetTick() can't advance
        while global interrupts are masked (it's SysTick-driven, and
        SysTick is masked too), the previous entry's wall-clock timeout
        doesn't work here -- replaced with a plain 1,000,000-iteration
        spin-count ceiling, deliberately loose (many milliseconds of
        real time even pessimistically) rather than tuned, so it can
        only ever trip on a genuine hang, never in normal operation.

        Verified: full clean rebuild, zero warnings. Reflashed, table
        re-uploaded, FIRE -> OK repeatedly (fired twice back to back),
        board stayed fully responsive to *IDN?/TABLE? throughout -- no
        hang, and no UART data loss from the masked window (a ~10 us,
        worst-case ~385 us mask is far shorter than the ~1 ms/byte
        margin at 9600 baud, so an in-flight RX byte just sits in the
        UART's hardware data register a little longer, unaffected).
        Re-capturing with DSLogic to confirm the residual actually
        shrank is the next step, not yet done as of this writing.

2026-09-04  —  Bugfix: cold-start phase-lock glitch on every FIRE
------------------------------------------------------------------
  Change:  Found via a real DSLogic U3Pro32 capture (decoded by hand --
        no capture-analysis tooling in this repo, just the .dsl
        archive's raw bit-packed channel data). Symptom: on every
        `FIRE`, U/V/W's first-ever output edges all landed on the
        exact same sample -- not staggered 120°/240° apart as
        intended -- producing ~1-2 garbled cycles (one phase measured
        holding ON ~7.4x too long; that first "period" reading as low
        as ~60 kHz) before self-correcting from cycle 2 onward. Matches
        what the user had independently noticed as "~60 kHz garbage for
        the first ~2 periods" on a real scope.

        Root cause: HRTIM1_PWM_Start()'s HAL_HRTIM_WaveformSetOutputLevel()
        calls (needed, per ST's own HAL guidance, to avoid an undefined
        complementary-pair state when DeadTimeInsertion is enabled)
        force TA1/TB1/TC1 all ACTIVE at the same instant, with no
        regard for their intended stagger. Timer A's ResetTrigger
        (MASTER_PER) happens to coincide with its own natural period
        rollover, but Timers B/C (ResetTrigger = MASTER_CMP1/CMP2)
        aren't genuinely phase-locked until they've received their
        first Master-CMPx-triggered reset -- which hasn't happened yet
        at the moment the counters first start.

        Fix: HRTIM1_PWM_Start() now starts the counters as before, but
        delays connecting the outputs to the pins (WaveformOutputStart())
        until the Master's own MREP (repetition) flag confirms one full
        period has genuinely elapsed in hardware -- by then every
        timer has already received its first phase-defining reset, so
        the first VISIBLE edge is already correctly phase-locked.
        Waiting on the hardware flag rather than computing a busy-wait
        from `per`/HRTIM_TIMER_CLK_HZ makes this automatically correct
        for whatever period is currently loaded -- no hardcoded 100 kHz
        assumption, so it stays correct if/when variable-frequency
        tables exist (per user request, 2026-09-04). HRTIM_MASTER_IT_MREP
        (armed at boot by HRTIM1_EnableMasterInterrupt(), and still
        armed from any previous shot) is masked for the duration of
        this wait and any stale flag discarded first -- otherwise
        PFM_CycleBoundaryHandler() would fire for real during the
        settling wait and silently advance the table to step 1 before
        step 0 was ever visible on the pins. Bounded to 5 ms
        (>12x margin over the ~385 us worst-case period a uint16_t
        `per` can represent) with an Error_Handler() fallback, matching
        this file's existing defensive-timeout convention (see
        HAL_HRTIM_PollForDLLCalibration() in HRTIM1_FullInit()).

        Verified: full clean rebuild (make clean && make all -j4, zero
        warnings; text grew 88 bytes). Verified on real hardware:
        reflashed over serial, re-uploaded a 500-entry table, sent
        FIRE -> OK promptly (no hang from the new bounded poll -- the
        real risk this change introduced), board stayed responsive to
        *IDN? immediately after. Re-capturing with DSLogic to confirm
        the actual edge timing is now clean is the next step, not yet
        done as of this writing.

        problem.

        the port's timeout only on a genuine no-reply failure, which
        still needs to time out and raise). No protocol or firmware
        change. Verified: a real 500-entry upload (profile 1) dropped
        from 500-1000+ s to 20.2 s measured wall-clock, same successful
        `TABLE:END -> OK 500` result.

        Considered and deferred (see the FIRE entry below's own
        real-hardware pass for why 20 s was accepted as fine for now):
        batching multiple TABLE:STEP entries per line (needs a
        firmware/protocol change; marginal win once the read-loop bug
        is fixed, since ~30 s of raw payload at 9600 baud is close to
        the real floor for 500 entries either way) and pipelining
        without waiting for each ACK (real risk of silently overrunning

2026-08-31  —  Bugfix: ROM bootloader Go-jump left interrupts dead
---------------------------------------------------------------------
  Change:  Found and fixed on real hardware while first testing
        wham_serial_flash.py end-to-end. Root cause, symptom, and fix
        are documented in full in boot_jump.c's BootJump_CheckAndEnter()
        and in docs/serial_reflash_guide.md Section 4 -- summary:

        Symptom: a serial reflash reported success (write + verify both
        passed via stm32flash), but the newly-flashed firmware was
        completely unresponsive over USART2 afterward -- *IDN? got no
        reply -- until the board was power-cycled, at which point it
        worked immediately and correctly.

        Root cause: stm32flash's -g (the ROM bootloader's "Go" command)
        branches to the new app without performing a real chip reset.
        SCB->VTOR and SYSCFG->MEMRMP, left pointing at the ROM
        bootloader's own vector table from the *previous* boot's jump
        INTO the bootloader (the normal BOOT-command flow), are never
        corrected by anything in this firmware -- system_stm32g4xx.c's
        SystemInit() only sets VTOR under USER_VECT_TAB_ADDRESS, which
        is not defined here (the CubeMX default). Every interrupt,
        including the USART2 RX interrupt the whole command parser
        depends on, vectored into the ROM bootloader's table instead of
        the app's own.

        Fix: BootJump_CheckAndEnter()'s normal-boot path now
        unconditionally restores SCB->VTOR = FLASH_BASE and the main-
        Flash SYSCFG remap before falling through to HAL_Init(). No-op
        on a true reset (both already correct there); the actual fix on
        the Go-jump path.

        Verified: flashed a new firmware version over serial, queried
        *IDN? immediately with no manual reset, got the new version back
        correctly -- confirmed twice in a row (v0.5, then v0.6).

        Not yet ported to the sibling PFM-STM32G474/-V4 projects, which
        carry the same unfixed boot_jump.c this one was forked from --
        deliberately deferred per project decision, not forgotten.

2026-08-31  —  SCPI-style hierarchical command dispatch
-------------------------------------------------------------
  Change:  Replaced cmd_parser.c's flat case-sensitive exact-match table
        with SCPI-style matching (scpi_match()/scpi_token_match()):
        colon-separated hierarchy levels, per-level short/long form
        (mandatory-uppercase-prefix + optional-lowercase-suffix),
        case-insensitive, exact query-suffix (?) matching, tolerant of
        a leading colon on input. Table stays flat (one row per leaf
        command, full mnemonic path as the pattern) -- no separate tree
        structure to build or maintain.

        Verified with a standalone native (non-cross-compiled) test
        harness before wiring in: 19 cases covering short/long form,
        mixed-form, wrong depth, wrong query suffix, case variants, and
        leading-colon tolerance, all passing. Also confirmed strtok_r/
        strncasecmp/isupper actually link under this toolchain's
        --specs=nano.specs (not guaranteed in every newlib-nano config).

        *IDN was renamed to *IDN? to match real IEEE 488.2/SCPI form,
        now that the trailing ? is meaningfully enforced.
